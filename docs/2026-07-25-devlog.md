### Broken logo on Terms

`terms.html` pointed its header logo at `/figmaAssets/layer-1.svg` — a path that has never existed
in this repo; every other page correctly used `/assets/design-dept-logo.svg`. It was a leftover from
a Figma export.

The failure was invisible in the HTTP status: Cloudflare Pages answers a missing path by serving
`index.html` with a **200**, so the request "succeeded" while returning `text/html` to an `<img>`
tag — a broken image in the browser. Worth remembering when checking assets on Pages: status codes
lie here, check `content-type` instead.

## Cloudflare audit

The question was what it takes to push to production. Answer: `git push origin main`. Nothing else.

| Item | Finding |
|------|---------|
| Nameservers | `chin.ns.cloudflare.com` / `donovan.ns.cloudflare.com` |
| Host | Cloudflare Pages |
| Pages project | `design-dept.pages.dev` |
| Custom domain | `designdept.com` + `www`, both proxied |
| Deploy source | GitHub `khoivinh/design-dept-site`, branch `main` |
| Build command | None — static files from repo root |

**The repo contains zero Cloudflare configuration** — no `wrangler.toml`, `_headers`, `_redirects`,
or `.github/workflows`. Every deploy setting lives in the Cloudflare dashboard. That means the repo
can't tell you how it deploys; this devlog and `STATUS.md` are the only record.

Two edge behaviors that make the deployed HTML differ from the source, both expected:

- **Email obfuscation.** `mailto:hellodesigndept@gmail.com` is rewritten at the edge into
  `/cdn-cgi/l/email-protection` plus an injected decoder script. A dashboard feature, not a repo diff.
- **`.html` is stripped.** `/terms.html` 308-redirects to `/terms`. Internal links still use the
  `.html` form and therefore take an extra hop. Harmless, but it briefly made verification look
  like a failed deploy — a `curl` without `-L` returns an empty body.

## Push identity

The first two push attempts were rejected: `push declined due to email privacy restrictions`.

The repo's entire prior history is authored as `Khoi Vinh <public@subtraction.com>` with commit
messages like `Update terms.html` — every previous edit was made in the GitHub web editor, so a
command-line push had never been attempted. GitHub's "block command line pushes that expose my
email" setting rejects *any* non-noreply address, so matching the historical address didn't help
either.

Resolved with a **repo-local** `user.email` of `982380+khoivinh@users.noreply.github.com`. Global
config is untouched; only this repo is affected. The tradeoff is that new commits are attributed to
the noreply address rather than `public@subtraction.com`, so the history now shows two identities.
Turning off the GitHub setting and resetting `user.email` would undo it.

**Open consequence:** Pages answers a deleted path by serving `index.html` with a **200**, so
`/sms-consent.html` will silently return the homepage rather than a 404. Anyone still holding that
link — including a carrier verifying A2P 10DLC registration — gets a page that looks live. A
`_redirects` entry (301 to `/`, or a 410) would be the honest answer. Not done; flagged.

Deleting the page also doesn't withdraw the toll-free number's carrier registration. That's an
account-side action, separate from the website.

## Two truncated files repaired

Both `contact.html` and `cancellations.html` were **cut off mid-document** in the committed
history — a pre-existing defect, not introduced here:

- `contact.html` ended at `<script>document.que` — no closing `</script>`, `</body>`, or `</html>`.
- `cancellations.html` ended mid-sentence inside the SMS paragraph, with no `</p>`, no `</main>`,
  **and no footer at all** — that page has been shipping without its footer navigation.

Browsers paper over this with error recovery, which is why it went unnoticed. `cancellations.html`
surfaced only because the SMS section I was removing *was* the truncation point; `contact.html`
surfaced from a structural sweep afterward.

Both now close properly and carry the standard footer. All five pages verify 1:1 on doctype,
`</body>`, `</html>`, `</main>`, `</footer>`, and the year script, with matching nav (2) and footer
(4) link counts.

Worth noting the likely cause: every prior commit was made through the GitHub web editor, and a
truncated save there would produce exactly this. Worth a structural check after any future web-UI
edit.

## Verifying behind email obfuscation

Cloudflare Pages has Email Address Obfuscation enabled, so the deployed HTML never contains the
literal address — it's rewritten into `/cdn-cgi/l/email-protection` with the address hex-encoded in
a `data-cfemail` attribute. Grepping the live page for `hello@designdept.com` therefore returns
nothing whether or not the deploy succeeded, which is a silent false negative.

Decoding is simple: the first byte of the hex string is an XOR key, and each subsequent byte is a
character XORed with it.

```
h = data-cfemail value
k = int(h[:2], 16)
''.join(chr(int(h[i:i+2], 16) ^ k) for i in range(2, len(h), 2))
```

Confirmed all five pages decode to `hello@designdept.com`. **Use this to verify any future email
change** — a plain grep will mislead.

Also worth noting the deploy took roughly 45 seconds; the first two polls still decoded to `admin@`.
Verifying too early reads as a failed deploy.

# Part 2 — SMS page restored as a parked placeholder

Shipped as `7c73966`.

## `/sms-consent.html` exists again, deliberately unlinked

The SMS channel is dormant but may be reactivated, so rather than a redirect or a 410, the page is
back — which also resolves the 200-serving-the-homepage problem on its own.

**It is a true orphan by design.** The instruction was not to link it from the Contact page, and
since the nav and footer are duplicated into *every* page, any nav or footer entry would have
appeared on Contact too. So there is no nav link, no footer link, and no `sitemap.xml` entry
anywhere on the site. The only reference to the URL is the page's own `rel="canonical"`. It is
reachable solely by typing the address.

No `noindex` was added. With the page unlinked and absent from the sitemap, crawlers are unlikely to
reach it anyway, and a `noindex` would become a silent gotcha on reactivation.

## The page does not name a messaging number — on purpose

Every version of this page previously hung on `+1 (855) 574-9839`, which is no longer published
anywhere on the site. Asserting an opt-in number that doesn't accept messages would be worse than
naming none, so the page opens with an explicit "this messaging program is not currently active"
disclosure and describes the terms conditionally.

Everything a carrier looks for is still present and ready to activate — express consent, opt-in
mechanism, program details, frequency, cost disclosure, STOP, HELP, not-a-condition-of-purchase,
privacy, and a full contact block with the physical address.

**To reactivate:** insert the SMS-capable number in the Express Consent / How You Would Opt In
sections, drop the inactive-program disclosure, switch the conditional phrasing to present tense,
and add the page back to `sitemap.xml`. Whether it also gets a nav or footer link is a separate
call, since that would put it on the Contact page.
